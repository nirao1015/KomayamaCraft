# TASK-M00-05 解放条件定義

## 目的

地域、設備、レシピ、自動化、Tierの利用可否を、コードへ個別条件を書かずデータから判定できる構造にする。

## 作業範囲

- `UnlockDefinition`をScriptableObjectとして実装する。
- 解放ID、表示情報、前提条件、解放対象を設定できるようにする。
- 複数条件のANDを表現できるようにする。
- 将来必要になった場合にOR条件を追加できる構造にするが、M0では複雑な条件エディタを作らない。
- 少なくとも次の条件種別をデータで表現できるようにする。
  - 別の解放フラグが成立済み
  - 指定Tierへ到達済み
  - 指定アイテムの納品済み数量
  - 指定設備の建設済み
- 条件成立前と成立後の状態を保存できる形にする。
- M1では条件なしで利用可能な検証データを作成する。

## 対象外

- 経験値、スキルツリー、契約固有の詳細条件
- 解放演出
- Tier 1からTier 2への実際の遷移
- 汎用ビジュアル条件エディタ

## 完了条件

- [x] 条件なし、単一条件、複数AND条件をデータで表現できる。
- [x] 解放対象がアイテム表示名などに依存しない。
- [x] 循環参照と存在しない解放IDを検出できる。
- [x] 解放済み状態を永続IDで保存できる。
- [x] 新しい解放データの追加にコード変更を必要としない。

## 確認方法

1. 条件なし、1条件、2条件ANDの検証データを作成する。
2. 条件状態を変え、期待する解放可否になることを確認する。
3. AがBを、BがAを前提とするデータを作り、循環参照として検出されることを確認する。

## 実装メモ

「素材を所持している」「納品した」「完了報告した」「機能を解放した」は別状態として扱う。単一のboolへまとめない。

## 成果物

- `UnlockDefinition` / `UnlockDefinitionCatalog`
  - 条件なし、単一条件、複数AND、および複数ANDグループ間のORを同じ構造で定義する。
  - 解放対象をアイテム・レシピ・設備・資源発生点の定義参照、機能・地域の安定識別子、Tier番号で指定する。
- `UnlockCondition` / `UnlockConditionGroup`
  - 別の解放フラグ成立、Tier到達、アイテム納品済み数量、設備建設済み数量を条件種別として保持する。
  - アイテム所持数、納品済み数量、完了報告、解放済み状態は統合しない。
- `UnlockStateRecord`
  - 解放IDと解放済み状態だけを保存する最小レコード。条件評価に使う進行値は各進行データ側で別に保存する。
- `GameDataCatalogs.KomayamaUnlocks`
  - `Resources/GameData/KomayamaUnlockCatalog.asset`を読み込み、永続IDで定義を取得する。
- M1検証データ
  - 条件なし解放`unlock.prototype_unconditional`
  - 解放対象となる機能識別子`m1_prototype_access`

## 保留

- 解放条件の実際の進行評価、状態更新、解放演出は対象外とする。

存在しない前提解放IDと解放定義間の循環参照の横断検出は、M00-06の`KomayamaGameDataValidator`へ統合済み。
